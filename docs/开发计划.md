# Galgame 管理器开发计划

| 版本 | 日期 | 计划工期 | 估算基准 |
| --- | --- | --- | --- |
| v0.1 | 2026-11-20 | 4 周，共 20 个工作日 | 单人开发，每个工作日 6 小时，共约 120 小时 |

首版交付 Windows x64 自包含压缩包。用户解压后可选择扫描目录，确认导入结果，在游戏库里搜索和启动游戏，并能修复失效的启动路径。工期以正式开工日为第 1 个工作日，包含联调、双系统验收和发布缓冲。实际日期随开工时间与可投入工时确定。

## 1 开工准备与资源需求

| 资源 | 当前状态 | 准备方式与时间 |
| --- | --- | --- |
| Windows 11 x64 开发机 | 已检查，本机可用 | 第 1 天确认能以普通用户构建和运行。 |
| .NET 10 SDK x64 | 环境检查时未检测到 | 第 1 天安装并执行 `dotnet --list-sdks`，然后构建并启动一个 WPF 工程。 |
| 编辑器、版本管理和包源 | VS Code、Git 和 WinGet 可用，NuGet 已连通 | 第 1 天建立 Git 仓库，确认依赖可还原。按需安装 VS Code C# 扩展。 |
| Windows 10 22H2 x64 测试环境 | 需要准备实机或虚拟机 | 第 1 天确认可用环境，第 2 天用最小发布包验证。测试时记录系统版本、内部版本号、架构和是否预装运行时。 |
| Windows 11 x64 验收环境 | 可用本机 | 第 4 周用与 Windows 10 相同的包回归。 |
| 游戏与测试样本 | 开工时建立 | 准备至少 5 款有权测试的本地游戏，覆盖单入口、多入口、嵌套入口、中日文及空格路径。另备一个可报告收到的参数与工作目录的测试程序，并构建约 5,000 个目录的合成扫描集。 |
| 项目依赖与发布工具 | 随工程配置 | 使用 WPF、`Microsoft.Data.Sqlite` 和 .NET CLI。拉取依赖、运行测试、生成自包含 ZIP 所需的命令随源码记录。 |

初次验证优先确认两个技术点。用最小 WPF 程序验证 Windows 10 能解压运行并打开选择目录对话框，再用测试程序验证启动工作目录和参数。这两项在主界面和识别规则投入开发前完成。

## 2 时间线与任务分配

开发者承担实现、测试、排查和打包。项目负责人负责确认范围和最终验收，可由同一人兼任。以下按工作分段安排，工时包含段内自测。

| 工作日 | 任务与负责人 | 依赖 | 工时 | 完成条件 |
| --- | --- | --- | ---: | --- |
| 第 1–2 天 | 开发者安装 SDK、建仓、创建 WPF 工程，验证目录选择和启动参数。项目负责人确认 Windows 10 验收环境。 | 开发机、Windows 10 测试环境、NuGet | 12 h | 工程能构建，最小发布包在两种系统启动。测试进程收到正确工作目录。 |
| 第 3–5 天 | 开发者实现 SQLite 建库、迁移、目录与游戏仓储，搭好游戏库和名称搜索。 | 工程和数据模型 | 18 h | 可以写入、查询和重新加载游戏与扫描目录。唯一键和外键行为通过测试。 |
| 第 6–9 天 | 开发者实现目录遍历、取消和进度，按规则归组并评分。用游戏样本调整阈值。 | 路径规范、样本目录 | 24 h | 单入口、多入口、嵌套入口、重叠根和坏目录都能产生预期结果。 |
| 第 10–12 天 | 开发者实现扫描目录管理、导入预览、入口选择和事务写入。 | 扫描服务、仓储、游戏库 | 18 h | 能从文件夹选择走到入库。重复导入和取消预览时，数据库维持预期状态。 |
| 第 13–15 天 | 开发者完成一键启动、手动添加、游戏详情和路径修复。 | 游戏库、进程启动原型 | 18 h | 玩家可在应用内修改配置并启动。移动目录后可重新定位并再次启动。 |
| 第 16–18 天 | 开发者执行双系统兼容测试、场景回归和扫描响应测试。 | 功能齐备的自包含包、测试环境 | 18 h | 记录两个系统的测试证据，定位并处理阻断问题。 |
| 第 19–20 天 | 开发者修复和回归、生成 ZIP、整理使用说明。项目负责人核对验收结果。 | 完成回归、无阻断问题 | 12 h | 发布包和使用说明齐备，同一个包在双系统上通过最终冒烟测试。 |
| **合计** | | | **120 h** | |

第 1 周结束时完成基础工程和数据库验证。第 2 周结束时可以用样本验证扫描结果。第 3 周结束时完成从选择目录到启动和修复的完整流程。第 4 周完成回归和交付，其中第 19 天优先用于兼容修复和缓冲。

## 3 任务依赖与进度管理

关键依赖是 **构建环境 → 目录扫描与识别 → 导入与保存 → 完整流程联调 → Windows 10 和 11 验收**。数据库初始化与进程启动原型可独立验证。识别规则调整以样本结果为依据，排期优先保证手动选择入口和手动添加可用。

用一个项目任务清单记录每项任务的负责人、预计与实际工时、依赖、验收条件和关联需求编号。工作日结束时更新已完成、进行中和阻塞项。每周末对照当周完成条件，并依据剩余工时更新交付预测。新增功能依据是否影响 R01 至 R07 的验收排入当前版本或后续版本。

## 4 测试与验收

自动化优先覆盖入口排序、路径归组和去重、参数序列化、数据库迁移及事务回滚。WPF 交互与真实游戏启动用手工测试，记录操作系统版本、应用构建标识、样本类型、测试结果和失败详情。

| 用例 | 需求 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| T01 目录与取消 | R01 | 从两个有重叠的目录开始扫描，另加入一个访问失败的分支，并测试取消。 | 进度可见，失败分支有提示，其余结果可用。取消后未产生导入记录，窗口保持可操作。 |
| T02 入口识别 | R02 | 分别扫描单入口、带卸载工具、原版与汉化版并存及入口位于程序子目录的游戏。 | 同一安装目录归为一项。辅助程序不会被自动预选。入口不明确时可以手选或保存为待配置。 |
| T03 游戏库和持久化 | R03 | 导入游戏，按名称搜索并重启应用。 | 显示名称和搜索匹配正确，重启后导入记录与目录配置可恢复。 |
| T04 启动参数 | R04 | 通过游戏库启动使用相对资源路径的程序，传入带空格、引号和空字符串的参数。 | 程序能加载资源，收到的工作目录和参数逐项匹配。真实游戏样本进入预期界面。 |
| T05 路径修复 | R05 | 移动已导入的游戏目录，或断开并重新接入移动盘。 | 原条目保留。路径失效时有提示，重新连接或重新定位后能再次启动。 |
| T06 去重与事务 | R06 | 用重叠根重复扫描，修改过名称和入口后再次导入，并模拟数据库写入失败。 | 同一安装路径只有一条，用户配置保留。故障批次整体回滚，重试可用。 |
| T07 双系统发布 | R07 | 将同一 ZIP 解压到 Windows 10 22H2 x64 和 Windows 11 x64，使用普通用户运行。 | 两边都通过选择目录、导入、搜索、重启后读取和启动。Windows 10 使用未预装 SDK 或桌面运行时的环境，记录系统版本和补丁。 |
| T08 批量扫描响应 | R01 | 扫描约 5,000 个本地目录。扫描中移动窗口、搜索已有游戏，再取消。 | 窗口和搜索仍可操作。当前文件系统调用返回后，扫描停止继续遍历。 |

Windows 10 首先验证 22H2 x64 的家庭版或专业版，报告明确列出实际验收的版本。发布说明按实测记录兼容范围。`.NET 10` 的官方支持范围和应用实测结果各自留档。 [微软 .NET 10 支持清单][dotnet-os]

### 发布门槛

- R01 至 R07 全部通过。阻止应用打开、扫描入库、持久化或启动的缺陷均已修复并复测。
- Windows 10 测试环境验证自包含 ZIP，无需预装 .NET SDK 或 .NET 桌面运行时即可打开主界面。游戏各自的运行依赖随样本记录。
- 使用相同版本的 ZIP 完成 Windows 11 回归。发行内容包括应用压缩包、解压与导入说明、已验证的系统版本和已知限制。
- 源码、可复现的构建步骤、测试用例和验收结果归档到项目。数据库迁移应经过重复打开验证。

## 5 风险与应对

| 风险 | 最早发现时点 | 应对 |
| --- | --- | --- |
| Windows 10 环境未落实或最小发布包无法启动 | 第 1–2 天 | 优先补齐实机或虚拟机。复现启动失败并核查 .NET、原生依赖和系统 API，完成最小验证后再锁定发布配置。Windows 10 验收结果计入发布门槛。 |
| 文件名和目录结构导致误识别 | 第 6–9 天 | 记录样本的期望入口，调试评分与归组。保持低置信度交由用户确认，手动添加用于覆盖特殊目录。 |
| 重叠目录、盘符改变或搬迁导致重复记录 | 第 10–15 天 | 测试规范路径键、重复提交和重新定位，按原 ID 更新配置。 |
| 旧游戏依赖工作目录、区域设置或运行库 | 第 2 天及第 13–18 天 | 用测试程序先验证应用传参，用真实样本区分应用启动错误和游戏进程内部错误。 |
| 实际投入低于工时估算 | 每周结束 | 以剩余工时滚动调整交付日期。优先完成扫描、入库和启动，再打磨评分和界面细节。 |
